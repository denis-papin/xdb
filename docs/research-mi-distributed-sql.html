Prioritized Micro-Instructions for Distributed PL/SQL

Research note · XDB project · November 2026 · Status: design exploration, nothing built yet

In one paragraph. A PL/SQL-like procedure ("the code") is compiled into a dependency graph of small, restartable micro-instructions (MIs). Each MI touches one shard. MIs are shipped to the node that owns the data and run there, out of order, as soon as their inputs are ready — the way a CPU issues micro-ops. Conflicts are not handled by a lock manager. Instead every transaction carries one fixed, globally ordered priority (its age). When two MIs collide on a record, the record's owner compares priorities: the older transaction wins, the younger one waits or is restarted. This is the classic wound-wait rule, and it gives serializability without deadlock detection. Replication uses one Raft group per shard; commits use a replicated two-phase commit.

1. Goals and assumptions

Goals

  • Run procedural code next to the data. Variables, IF, loops, cursors, exceptions and SQL statements inside one transaction.
  • Full ACID across shards. The target isolation level is serializable. Weaker levels are an optimisation, not the default.
  • Sharded and replicated storage. Losing one node per shard must lose no committed data and must not stop the cluster.
  • Minimal locking. No central lock manager, no deadlock detector, no lock table separate from the data.
  • Exploit parallelism inside one transaction. Independent statements of the code should run at the same time on different shards.

Design principles (used to settle every choice)

  1. Behave like a real transactional database. When in doubt, copy the semantics a PL/SQL developer already knows from Oracle, even if a newer idea looks nicer on paper.
  2. Be fast on a small LAN cluster. The reference size is 1–5 shards and 2–4 replicas per shard.
  3. Use only proven mechanisms. Every building block must already run in production in at least one known system. New ideas stay in "Alternatives" or "Open questions" until a prototype proves them.

Assumptions

  • One LAN, one data centre. Round trip 20–100 µs with kernel TCP, 3–10 µs with RDMA. Not designed for WAN.
  • Bounded clock skew. NTP gives about 0.1–1 ms on a LAN, PTP gives under 10 µs. We need a bound, not perfect clocks.
  • Crash-stop failures. Nodes crash and restart; they do not lie (no Byzantine faults).
  • OLTP workload. Short to medium transactions that touch tens to thousands of rows. Large analytic scans are out of scope.
  • Durable local storage. NVMe with fsync of 20–100 µs, or battery-backed memory.

2. Architecture

Components

  • Compiler. Parses the code, binds it to the schema, and produces an MI graph. Plans are cached per procedure and schema version, like Oracle caches compiled PL/SQL.
  • Coordinator. Owns the transaction record: id, priority, status (RUNNING, PREPARED, COMMITTED, ABORTED), and the list of shards touched. The record itself is stored in a shard, so it is replicated and survives the coordinator's crash.
  • Dispatcher. Looks up which shard owns each key (a cached range map) and sends MIs to that shard's leader. It batches MIs going to the same node.
  • Shard leader. Runs an MI scheduler (one per CPU core, see §4), holds the MVCC data and the write intents, and replicates its log to followers.

3. From the code to micro-instructions

3.1 Running example

PROCEDURE transfer(p_from NUMBER, p_to NUMBER, p_amt NUMBER) IS
  v_bal NUMBER;
BEGIN
  SELECT balance INTO v_bal FROM account WHERE id = p_from;
  IF v_bal < p_amt THEN
    RAISE_APPLICATION_ERROR(-20001, 'insufficient funds');
  END IF;
  UPDATE account SET balance = balance - p_amt WHERE id = p_from;
  UPDATE account SET balance = balance + p_amt WHERE id = p_to;
  INSERT INTO ledger(id, src, dst, amt) VALUES (ledger_seq.NEXTVAL, p_from, p_to, p_amt);
END;

3.2 Compilation pipeline

  1. Parse and bind. PL/SQL grammar → AST, resolve tables, columns, indexes.
  2. Lower SQL statements to access paths. Each statement becomes point reads, range scans, index lookups or writes. WHERE id = p_from on a primary key becomes a single-key access.
  3. Build an SSA dataflow graph. Every variable assignment gets a new name. Each MI depends only on the values it really uses, not on the textual order of the code. This is the step that exposes parallelism.
  4. Partition by shard. Each MI is tagged with the key (or key range) it touches. The shard is computed at dispatch time, because parameters are known only then.
  5. Keep program order where data may overlap. Two statements that touch the same table are kept in program order unless their keys are proven different. Keys are often parameters, so the check is done at dispatch time on the real values, like a CPU's memory disambiguation (see the box in 3.4).
  6. Fuse. Consecutive MIs on the same key and shard with nothing remote in between are merged into one MI block, executed in one message. This is the database version of a CPU's macro-op fusion, and the same thing as CockroachDB's per-range request batching. Without it, fine-grained MIs drown in network messages.

3.4 The example as an MI graph

T#  prio = (hlc=1730716800.000123, node=4)   read_ts = prio.time
m1  GET_X   account[p_from]            → r1          @shard(p_from)
m2  GUARD   r1.balance >= p_amt else -20001          deps: m1   (fused with m1)
m3  PUT     account[p_from].balance = r1.balance - p_amt
                                                     deps: m2   (fused with m1)
m4  APPLY   account[p_to].balance += p_amt           deps: m3 only if p_to = p_from (checked at dispatch)
                                                     control dep on m2: speculative (experiment, see below)
m5  SEQ_NEXT ledger_seq                → n           deps: —
m6  PUT     ledger[n] = (p_from, p_to, p_amt)        deps: m5
m7  COMMIT                                           deps: m3, m4, m6, and m2 = true

Same-key check (a bug the first draft had). If a caller runs transfer(7, 7, 100), m3 and m4 touch the same row. Run out of order, m3 would overwrite the credit made by m4, and the balance would end 100 lower instead of unchanged. The compiler cannot know p_from ≠ p_to, so it adds a conditional dependency. The dispatcher compares the real keys and keeps program order when they are equal (for ranges: when they overlap). Any statement whose keys cannot be compared this way runs in program order.

Speculation, explained — an experiment, off in v1. In the code, the credit to p_to comes after the IF. The compiler sees that m4 does not use any value from m1; only the control depends on it. So it could issue m4 early, like a CPU predicting a branch. If m2 raises the exception, the transaction aborts and the intent left by m4 is discarded; nothing was ever visible. The cost of a wrong guess is a wasted intent, which may have blocked or wounded another transaction for nothing.

No production database does this. So v1 uses only write pipelining, proven in CockroachDB since 2018: the code runs in program order, the IF waits for the read, and the writes after it are then all sent at once without waiting for each other. That costs one extra round trip (§9). Speculation stays an experiment, measured against this baseline.

4.1 The per-core scheduler

Each node runs one thread per CPU core, and each shard is owned by exactly one core (thread-per-core, as in ScyllaDB). Redpanda proves this model works with one Raft group per partition, which is our setup. With 1–5 shards and a few cores per node, a "shard" in this document can be split into one Raft group per core. That removes all in-memory latches: two MIs on the same key are always on the same core, and that core runs one MI at a time. "Concurrency" inside a core is interleaving, never parallel access.

Each core loops forever:

loop:
  pull arrived MIs from the network ring into the ready queue
  pick the ready MI with the highest priority       # oldest transaction first
  run it to completion or until it hits a conflict  # microseconds, never blocks the core
  on conflict: apply the priority rule (§5) — park, or wound the other txn
  send results / acks (batched)
  every few µs: append the accumulated writes to the Raft log (group commit)

MIs never block a thread. A waiting MI is a parked data structure on the record's wait list, costing a few dozen bytes. This is what makes "MIs continuously executing" cheap: the CPU spends its time on ready work, highest priority first.

4.2 Where the code's state lives

Variables of the code live in the coordinator's frame. MIs carry the values they need as arguments and return results to the coordinator, which resolves dependencies and fires the next MIs. For a fused block running entirely on one shard, intermediate values stay on that shard. Moving the whole frame to the shard that does most of the work would save more round trips, but no SQL engine I know of does this for general procedures, so it is an open question (§13), not part of the design.

4.3 Loops and cursors

A loop whose trip count depends on data cannot be fully expanded at compile time. Strategies, from proven to experimental:

  • Bulk fetch proven A cursor FOR loop fetches rows 100 at a time instead of one by one, as Oracle has done automatically since 10g.
  • Pipelined writes proven The writes inside the loop are sent without waiting for each other, batched per shard (CockroachDB pipelining and batching). The commit waits for them all.
  • Set-oriented rewrite experiment FOR r IN (SELECT …) LOOP UPDATE … WHERE id = r.id; END LOOP becomes one SCAN plus one APPLY per shard, sent in parallel. SQL Server inlines scalar functions into queries (Froid, in production since 2019), but rewriting whole loops is still research (Aggify, DBridge). v1 does not do it.

5. Concurrency control by priority

This is the heart of your idea. The goal is to replace a lock manager with a rule that any shard can apply alone, using only local information plus the priority carried by each MI.

5.1 What a priority is

  • When a transaction starts, the coordinator takes a hybrid logical clock value (physical time + logical counter) and appends its node id: prio = (hlc, node_id). This is unique and totally ordered across the cluster, with no central service.
  • Lower value = older = higher priority.
  • The priority is fixed for the life of the transaction, including restarts. A transaction that was wounded restarts with its old priority, so it gets older relative to newcomers and eventually wins. This prevents starvation.
  • The same value is the transaction's MVCC read timestamp at first. It may be pushed forward (§5.4) but the priority is not.

5.2 What each record holds

record k:
  versions:    [(commit_ts, value), …]     # committed MVCC history, newest first
  intent:      none | (txn_id, prio, provisional_value)   # at most ONE writer
  max_read_ts: timestamp                   # highest ts that has read k
  waiters:     list of parked MIs, sorted by prio

The intent is the only "lock" in the system. It lives inside the record, costs no extra lookup, and is replicated with the data. There is no separate lock table.

5.3 The rules (wound-wait)

When an MI of transaction T arrives at record k, which carries an intent from transaction H (the holder):

SituationDecision
No intent, T readsRead the newest version with commit_ts ≤ T.read_ts. Raise max_read_ts. Never waits.
No intent, T writesIf max_read_ts > T.ts, a younger reader already saw the old value: push T's commit timestamp above it (§5.4). Then place the intent.
Intent from H, T is older than HWound H. Mark H's transaction record ABORTED (if it is still RUNNING), remove its intent, proceed. H restarts later with its old priority.
Intent from H, T is younger than HWait. Park T's MI on waiters. It wakes when H commits or aborts.
Intent from H, H is already PREPAREDWait, whatever the priorities. A prepared transaction can no longer be wounded (it may already be committed elsewhere). Prepare is short, so the wait is short.
T only reads, H's intent has a timestamp above T's read_tsIgnore the intent and read the older version. MVCC means most reads are never blocked.

Why no deadlock is possible. A transaction only ever waits for an older one. So every "waits-for" arrow points from younger to older. Arrows that always point in the same direction of a total order cannot form a cycle. No shard needs to know anything about other shards' waits — the rule is local and the result is global. This is exactly what you were after: the priority replaces deadlock detection.

Why it is serializable. Write–write conflicts are ordered by intents (one writer per record, like strict two-phase locking for writes). Read–write conflicts are ordered by timestamps (MVCC plus max_read_ts, like timestamp ordering). Commit timestamps are chosen so that every transaction's reads and writes are consistent at one point in time. This is the same family of protocol as CockroachDB's serializable mode; the priority layer only decides who waits.

5.4 Timestamp pushes and read refresh

When T's commit timestamp must move forward (a younger reader saw a key T wants to write), T's earlier reads may no longer be valid at the new timestamp. Before commit T runs a cheap refresh: it asks each shard "has any key I read changed between my old and new timestamp?". If not, T commits at the new timestamp with no restart. If yes, T restarts (keeping its priority). The coordinator keeps the read set for this, as key ranges, not values.

5.5 Priority classes

Pure age has one drawback: a long batch job becomes very old and wounds every short interactive transaction it meets. The fix is to put a class in the most significant bits:

prio = (class, hlc, node_id)      # class 0 = system, 1 = interactive, 2 = batch

The order is still total and fixed per transaction, so the deadlock-freedom argument still holds. User-chosen classes are proven: CockroachDB has LOW/NORMAL/HIGH transaction priorities that decide who wins a conflict. The class never changes automatically. A batch job can therefore be delayed by a constant stream of interactive work. The proven answer is to keep batch blocks small (§7.4), so each one has a short window to be wounded in. Automatic promotion after N restarts is an open question (§13).

5.6 Priority inversion

A high-priority transaction can wait on a PREPARED low-priority one. This wait is bounded: a prepared transaction only needs one more consensus round (about 80 µs) to finish. v1 therefore does nothing special. Priority inheritance ("boosting" the holder) is proven in real-time operating systems, not in distributed databases, so it is listed as an open question.

6. Sharding, replication and commit

6.1 Sharding

  • Range sharding on the primary key, automatic split at ~256 MB or on load, automatic merge. Range sharding keeps scans local; hash sharding would spread hot sequential inserts but kill range scans.
  • Co-location by key design. Child tables start their primary key with the parent's key, e.g. order_line keyed by (customer_id, order_id, line). With range sharding, a customer's rows then usually sit on one shard, and most procedures touch a single shard — the cheapest case by far. A stronger feature, "interleaved tables", forces parent and child rows into the same range. Spanner has it, but CockroachDB removed it in 2021 because it cost more than it saved. v1 relies on key design only.
  • Secondary indexes are separate ranges, so an index update is a second MI, often on another shard. That is a real cost (§10).

6.2 Replication

One Raft group per shard, 3 replicas by default (see the table below for the 2–4 range). The leader holds a time-based lease, so it can serve reads without a Raft round. Intents and the transaction record are written to the Raft log like data, so a new leader knows every intent after a failover.

Writes are applied to the leader's memory immediately (so later MIs of the same transaction see them), but the transaction cannot commit until the intents are durable on a majority.

How many replicas, for the 2–4 range

A majority-based protocol counts votes, so the number of replicas does not translate directly into safety:

ReplicasCommit waits forFailures toleratedVerdict
2both0 — one failure stops writesAvoid. Twice the storage, no availability gain.
2 + 1 witness2 of 3 votes1Good when storage is expensive. The witness keeps only the log, not the data. While one data replica is down, only one full copy of the data exists until repair. Proven: Spanner witness replicas; same idea as a cluster quorum witness.
32 of 31Default. Commit waits for the faster of the two followers.
4 (all voting)3 of 41Avoid: same failure tolerance as 3, slower commit.
3 voting + 1 learner2 of 31Use when a 4th copy is wanted for reads or backup. The learner gets the log but does not vote. Proven: Raft learners (etcd, TiKV), CockroachDB non-voting replicas.

6.3 Commit

  • One shard: a single Raft write turns intents into committed versions. One fsync, one LAN round trip to followers.
  • Several shards: two-phase commit where the coordinator's transaction record is itself a Raft-replicated key. Because participants and coordinator are all replicated, 2PC does not have its classic blocking problem.
  • Parallel commit optimisation (from CockroachDB): write intents and the STAGING transaction record in parallel; the transaction is committed as soon as all are durable. The client gets the answer after one consensus round instead of two. Intents are cleaned up asynchronously.

7. Transaction blocks inside a routine

A routine is often more than one transaction. A batch procedure, for example, commits every few thousand rows. The code is then a sequence of blocks separated by COMMIT or ROLLBACK:

BEGIN
  … block B1 …   COMMIT;
  … block B2 …   COMMIT;
  … block B3 …   -- ends with the call: implicit COMMIT, or ROLLBACK on error
END;

This section states exactly what is protected. Each choice follows the three design principles of §1: Oracle semantics, cheap on a small LAN cluster, already proven elsewhere.

7.1 What one block guarantees

Each block is one complete transaction, with the full guarantees of §5 and §6:

PropertyHowProven in
Atomic, across shards tooWrites are invisible intents until one replicated write sets the transaction record to COMMITTED. All writes appear at that instant, or none do.CockroachDB, Percolator/TiDB
ConsistentKeys, foreign keys and check constraints run as MIs inside the block, before commit.All SQL databases
Isolated (serializable)MVCC reads at one timestamp, one writer per record, wound-wait between writers.Spanner, CockroachDB
DurableCommit is acknowledged only once a majority of replicas has it on disk.Raft/Paxos systems

What is not protected — exactly as in Oracle: between two blocks, other transactions can read and change the data. B2 does not see the database "as B1 left it", only as it is when B2 starts. Isolation holds per block, not per routine.

7.3 Why the routine does not resume automatically after a crash

One could save the routine's variables and position inside each COMMIT, and let another node continue after a crash ("durable execution"). I considered it and left it out of the main design:

  • It is proven in workflow engines (Temporal, Azure Durable Functions), not inside a SQL engine running PL/SQL. That fails principle 3.
  • It changes semantics a developer relies on. In Oracle a dead session means a stopped routine, and the developer's restart logic assumes that. That fails principle 1.
  • Saving the state is cheap, but restoring it is not simple: open cursors, package state, temporary tables and session settings would all need saving too.

Instead the design supports the pattern every batch framework already uses: a progress table written in the same block as the work. Because both are in one transaction, the progress row is correct after any crash. Rerunning the routine continues where the last committed block ended. This is proven in Spring Batch's job repository and Oracle's DBMS_PARALLEL_EXECUTE chunk status.

PROCEDURE monthly_interest(p_month DATE) IS
  v_last NUMBER;
  v_n    PLS_INTEGER;
BEGIN
  SELECT last_id INTO v_last FROM job_progress
   WHERE job = 'monthly_interest' AND period = p_month;
  LOOP
    v_n := 0;
    FOR r IN (SELECT id FROM account WHERE id > v_last
              ORDER BY id FETCH FIRST 1000 ROWS ONLY) LOOP
      UPDATE account SET balance = balance * 1.01 WHERE id = r.id;
      v_last := r.id;
      v_n    := v_n + 1;
    END LOOP;
    EXIT WHEN v_n = 0;
    UPDATE job_progress SET last_id = v_last          -- same block as the work
     WHERE job = 'monthly_interest' AND period = p_month;
    COMMIT;                                            -- one block = 1000 accounts
  END LOOP;
END;

The same table also settles the one case no database can avoid: when the connection drops during a COMMIT, the client cannot know whether that block committed. Reading job_progress answers it.

7.4 Cost of a block on a small cluster

For 1–5 shards with 3 replicas (or 2 + witness), on the network assumptions of §1:

Block touchesCommit costNotes
1 shard≈ 80 µsOne consensus round: 1 RTT to the fastest follower + 1 fsync.
2–5 shards≈ 80–100 µsParallel commit: all shards replicate at the same time. With at most 5 shards the fan-out is at most 5 messages. Intent cleanup happens after the client has its answer.

So a routine that commits after every row is limited to roughly 10,000 blocks per second — the same problem Oracle has with "log file sync" waits. The guidance is the same as in Oracle: 100 to 10,000 rows per block. Smaller blocks pay the commit cost too often. Larger blocks hold intents longer, get wounded more often, and lose more work when they restart.

The proven techniques alone give most of the gain (430 → 200 µs). The experimental part of the MI idea adds 200 → 150 µs on this example. It adds more on procedures with many independent reads, and nothing on procedures that are one long chain of dependent statements (§10.4).

Throughput is bounded by the slower of: CPU per MI per core (target 1–3 µs for a point access → ~300k–1M MIs/s/core), and network messages (batching is essential). That is a property of serializability on a single row, not of this design.

10. Compromises

You asked me to say clearly where the design gives something up. Here they are, ordered by how much they move away from your original idea.

10.1 Priority alone is not enough — intents are still a minimal lock core

The pure idea would be: "no locks, only priorities, like a CPU". It does not work by itself, for two reasons:

  • A CPU has one memory and one clock; we have many nodes. A CPU core can squash and replay instructions within nanoseconds because the whole state is in one chip. Here, the conflicting MIs may run on different machines microseconds apart. Someone must remember "T is writing this record" until T commits. That memory is the intent.
  • Without a marker, a younger writer cannot know it must wait. Priorities decide who wins; intents tell that there is a contest.

So the compromise is: one intent per record, stored in the record, plus the wound-wait rule. No lock table, no lock modes, no lock escalation, no deadlock detector. Reads are lock-free thanks to MVCC. This is as close to "locking by priority" as I believe a correct distributed system can get.

10.2 Work is thrown away under contention core

Wound-wait resolves conflicts by restarting the younger transaction. On a hot record, many young transactions may be wounded repeatedly. Each restart costs network round trips and CPU. Mitigations:

  • Waiting is preferred over wounding when the holder is close to commit (it sent PREPARE).
  • Applications with one very hot row (a global counter) need a schema change (split counter), as in every distributed database.

10.3 The code must be restartable core

Because a transaction may be wounded and replayed at any time, everything before commit must be side-effect free outside the database and deterministic given the data it read. Consequences for PL/SQL compatibility:

PL/SQL featureStatusReason / replacement
Variables, IF, loops, exceptions, records, collectionsSupportedPure, restartable.
SELECT … FOR UPDATE, cursorsSupportedMaps to GET_X / SCAN with intents.
COMMIT/ROLLBACK inside the procedureSupportedSplits the code into blocks, each a full transaction; only the current block restarts. Cursors may stay open across a commit, with Oracle semantics. See §7.
SAVEPOINT / partial rollbackSupportedIntents carry a sequence number; rollback to savepoint drops later ones.
Autonomous transactionsRestrictedAllowed only for logging, and they run as a separate transaction with its own priority. They do not roll back when the calling block restarts (§7.2), so they may log the same thing twice.

10.4 Parallelism inside the code is limited by data dependencies medium

Code like "read A, use the result to find B, use B to find C" is a chain; no compiler can make it parallel. Each link costs one LAN round trip. Speculation (an experiment anyway) helps only for control dependencies, not data dependencies. On top of the proven v1 baseline, expect parallel issue to add tens of percent on typical procedures, not multiples. Co-locating data usually matters more.

10.5 MI granularity: messages versus parallelism medium

Very small MIs give maximum scheduling freedom but one network message each, and a message costs 10–50× more than the MI's work. Very large blocks need few messages but hold intents longer and expose less parallelism. The design compromise: the compiler produces fine MIs, then fuses everything that targets the same shard with no remote dependency in between. Granularity is chosen by the compiler, not by the programmer.

10.6 Clocks: bounded skew is an assumption medium

Priorities and timestamps come from hybrid logical clocks. Correctness of priority does not depend on clocks (any unique total order works). But external consistency (a transaction that starts after another one commits sees its writes) needs a skew bound, enforced by self-shutdown of drifting nodes. On a single LAN with NTP or PTP this is a weak assumption. The alternative, a central timestamp oracle (as in TiDB), is also proven. It removes the clock-uncertainty restarts but adds one round trip per transaction (about 50 µs here) and one more service to keep highly available. On a 1–5 shard cluster it is a realistic fallback if HLC uncertainty restarts turn out to be frequent.

10.7 Consistency over availability medium

Synchronous majority replication means: a shard that loses its majority stops serving writes. A shard with 3 replicas tolerates 1 failure; with 5, it tolerates 2. Every commit pays at least one LAN round trip and one fsync. I chose this because "transactional" in your request implies no lost commits. Asynchronous replication would cut latency by ~80 µs per commit but loses recent commits on failover.

10.8 Cross-shard transactions cost more medium

A transaction on one shard commits in one consensus round. Across shards it needs the replicated transaction record, intent resolution on each shard, and is more exposed to wounds. Schema design (co-location by key prefix) matters more than in a single-node Oracle database. Secondary indexes make even simple updates multi-shard.

10.9 Phantoms need range tracking minor

Serializable isolation must prevent a concurrent insert into a range another transaction scanned. Each shard keeps a compact interval structure of (range, max_read_ts). It is approximate (ranges are merged when memory is tight), which can cause unnecessary timestamp pushes, but never incorrect results.

10.10 Not an analytics engine minor

Large scans run as MIs too, but the store is row-oriented and the scheduler is tuned for short MIs. Long scans are split into chunks with low priority class so they do not starve OLTP. Real analytics should go to a column-store replica.

11. Alternatives considered

11.1 Deterministic ordering (Calvin-style): the "purest" priority

Take your idea to its extreme: give every transaction its priority before it runs, by putting all transactions into a replicated global log in batches of ~10 ms. Every shard then executes transactions in log order. No locks at all, no aborts from conflicts, no 2PC (every replica deterministically reaches the same result).

Why it is not the main design: the system must know each transaction's read and write set before it runs. PL/SQL code decides what to touch based on what it reads. Calvin handles that with a "reconnaissance" pass and a restart if the guess was wrong, which is costly for exactly the kind of code you want to run. Also, every transaction pays the batching delay (milliseconds), even when there is no conflict.

Where it is a good fit: procedures whose keys are all known from parameters (like transfer). A later version could run such procedures in a deterministic fast path and the rest through wound-wait. Mixing the two safely is an open research question.

11.2 Single-threaded partitions (H-Store / VoltDB)

Each partition runs one stored procedure at a time, start to finish, with no concurrency control. Extremely fast for single-partition procedures. Multi-partition procedures lock entire partitions and become very slow. Our per-core scheduler borrows the "one thread owns the data" part but keeps record-level concurrency.

11.3 Optimistic concurrency (OCC, Silo, TicToc)

Run without intents, validate at commit. Great under low contention, but under contention it aborts the transaction that did the most work, and starvation is hard to bound. Wound-wait with fixed priorities gives a guarantee that every transaction eventually commits.

11.4 Wait-die instead of wound-wait

Wait-die is the mirror rule: older transactions wait, younger ones abort themselves on conflict. It is also deadlock-free. It aborts more often (the younger dies even when the older is about to finish), but never needs to reach a remote transaction to wound it. Worth benchmarking both; the decision is a single function in the scheduler.

13. Prototype roadmap and open questions

Roadmap

  1. Single-node engine. MVCC store, intents, per-core MI scheduler, wound-wait. Hand-written MI programs, no compiler yet. Measure MIs per second per core.
  2. Deterministic simulator. Run many nodes in one process with simulated network and clock; inject crashes and delays. Check serializability with a history checker (e.g. Elle). Do this before real networking — it is the only practical way to find bugs in this kind of system.
  3. Sharding and Raft. Use an existing Raft library; range map; leases.
  4. Cross-shard commit. Transaction record, 2PC, then parallel commits.
  5. Compiler, subset of PL/SQL, proven techniques only. Variables, IF, point SQL, then cursors and loops, then exceptions, savepoints and transaction blocks. Program-order execution with pipelined writes, per-shard batching and bulk fetch.
  6. The experiment. Dataflow analysis, parallel issue of independent statements with the same-key check, then speculation, then set-oriented loop rewriting. Each one can be switched off and is measured against step 5.
  7. Benchmarks. TPC-C (its New-Order and Payment transactions are almost exactly stored procedures), plus a hot-key microbenchmark to tune priority classes and wound vs wait.

Open questions

  • Can deterministic execution (§11.1) and wound-wait coexist in one cluster, with one priority space?
  • How aggressive should speculation be? A wrong speculative intent can block or wound another transaction for nothing.
  • Should the coordinator frame migrate to the shard that receives most of a procedure's MIs, and how to decide that at run time?
  • What is the right priority-class promotion policy for batch jobs that keep getting wounded?
  • Is priority inheritance (boosting a lower-priority holder) worth it, given that the wait on a prepared transaction is already short?
  • Can commutative APPLY MIs be merged at the record instead of conflicting (escrow transactions, O'Neil 1986)? This would help hot counters, but no mainstream SQL database ships it.

Bottom line. Your idea — compile procedural code into concurrent micro-instructions and resolve conflicts by priority, like a CPU — is sound and close to what the best distributed SQL systems already do internally. The one thing that cannot be removed is a small marker per written record (the intent): priorities decide who wins, intents tell a shard that there is a contest. With that compromise you get serializable transactions, no lock manager and no deadlock detection, and the main price is restarted work under contention and some restrictions on what the code may do before it commits.

Every part of that is proven in production except one: issuing independent statements of the code in parallel, with speculation. That is the genuinely new part. It is built as a switchable experiment on top of a v1 that uses only proven techniques and already runs the example in about 200 µs instead of 430 µs (§9, §12.1).
